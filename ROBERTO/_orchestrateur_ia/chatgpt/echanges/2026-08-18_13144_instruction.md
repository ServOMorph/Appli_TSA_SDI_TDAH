Oui, je ferais exactement cette séparation, avec une nuance importante : **les `.md` sont la documentation du contrat, tandis que le YAML est la définition déclarative exécutable du workflow**. La logique de transition, elle, reste dans le moteur Python.

### 1. Responsabilité des quatre fichiers

| Fichier                   | Rôle                                                               | Exécutable ?       |
| ------------------------- | ------------------------------------------------------------------ | ------------------ |
| `AGENT_WORKFLOW.md`       | Explique le fonctionnement global des workflows ROBERTO            | Non                |
| `AGENT_STATE.md`          | Définit le contrat des états, événements, identités et persistance | Non                |
| `workflow/marie.yaml`     | Décrit formellement états + transitions + événements autorisés     | Oui, indirectement |
| `engine/state_machine.py` | Charge le YAML et applique les transitions                         | Oui                |

Donc je ne mettrais **aucune logique métier critique uniquement dans les Markdown**.

Par exemple, si `AGENT_WORKFLOW.md` dit :

```text
RECU → ANALYSE lorsque l'analyse commence
```

mais que `marie.yaml` autorise autre chose, **c'est le YAML qui fait foi pour l'exécution**. Le Markdown doit être maintenu comme documentation synchronisée avec le contrat exécutable.

---

## 2. Pour le moteur : bibliothèque d'abord, CLI ensuite

Je choisirais **une fonction/lib importable directement**, et non un script CLI comme interface principale.

Architecture :

```text
ROBERTO/
├── engine/
│   ├── __init__.py
│   └── state_machine.py
├── workflow/
│   └── marie.yaml
└── state/
    └── marie/
        └── <uuid>.json
```

Avec conceptuellement :

```python
machine = StateMachine("ROBERTO/workflow/marie.yaml")

machine.dispatch(
    element_id="...",
    event="json_received"
)
```

Puis :

```text
scripts/ingest_manual_tests.py
             │
             ▼
       StateMachine
             │
       ┌─────┴─────┐
       ▼           ▼
 workflow YAML   state/<id>.json
```

C'est préférable parce que **l'ingestion est déjà un programme Python**. Lui faire lancer un deuxième processus Python uniquement pour changer un état ajouterait une couche inutile.

---

## 3. Mais je construirais quand même une CLI très mince

Je ne choisirais donc pas entre « bibliothèque » et « CLI » comme deux architectures concurrentes.

Je ferais :

```text
                ┌─────────────────────────┐
                │ StateMachine             │
                │ logique réelle            │
                └───────────▲─────────────┘
                            │
             ┌──────────────┴──────────────┐
             │                             │
    ingest_manual_tests.py          CLI ROBERTO
       import direct              outil de diagnostic
```

La CLI pourrait ensuite permettre :

```bash
python -m ROBERTO.engine.state_machine \
    --event json_received \
    --id <uuid>
```

Mais elle utiliserait **exactement la même classe**.

Pas :

```text
CLI → logique A
ingest → logique B
```

mais :

```text
CLI ───────────────┐
                   ▼
             StateMachine
                   ▲
                   │
ingest_manual_tests┘
```

Cela sera très utile pour le diagnostic manuel et les tests.

---

## 4. Je modifierais légèrement le nom du moteur

Je préférerais même :

```text
ROBERTO/engine/state_machine.py
```

avec une API de ce genre :

```python
class StateMachine:
    def __init__(self, workflow_path, state_store):
        ...

    def get_state(self, element_id):
        ...

    def dispatch(self, element_id, event):
        ...

    def can_transition(self, state, event):
        ...
```

Et **le moteur ne connaît rien de Marie**.

Il ne doit pas contenir :

```python
if workflow == "marie_tests":
    ...
```

C'est précisément le rôle du YAML.

Le moteur doit savoir :

> « On me donne un état + un événement. Je consulte la définition du workflow. Si une transition correspond, je la réalise et je persiste le nouvel état. »

---

## 5. C'est aussi ce qui prépare les deux autres flux

Avec cette architecture, demain on pourra avoir :

```text
workflow/
├── marie.yaml
├── google_drive.yaml
└── sync_marie.yaml
```

et toujours :

```text
engine/state_machine.py
```

Le moteur reste générique.

Les spécificités sont dans les définitions des workflows et, plus tard, dans leurs adaptateurs/actions.

C'est important parce que **l'Objectif 2 (le skill générique) émergera naturellement de cette séparation**. On ne cherche pas à fabriquer prématurément le skill ; on construit une architecture dont les responsabilités sont déjà séparées.

# Une distinction que je figerais dès maintenant

Il faut séparer **transition** et **action**.

Par exemple :

```text
RECU
  │
  │ event = analyse_started
  ▼
ANALYSE
```

La transition dit :

```text
RECU → ANALYSE
```

Mais elle ne devrait pas nécessairement contenir toute la logique :

```text
"lancer Claude"
"modifier tel fichier"
"appeler Supabase"
```

Je verrais plutôt :

```yaml
transition:
  from: RECU
  event: analyse_started
  to: ANALYSE
  action: start_analysis
```

Le moteur effectue la transition et pourra ensuite déléguer l'action à un composant approprié.

**Pour l'étape 2, toutefois, je n'implémenterais pas encore un système complexe d'actions/plugins.** Le premier moteur doit simplement prouver :

```text
charger YAML
→ charger état
→ recevoir événement
→ vérifier transition
→ modifier état
→ enregistrer transition
→ sauvegarder
```

C'est suffisant pour notre premier cycle Marie.

### Donc l'ordre précis devient

```text
1. Auditer marie_tests_journal.json + ingest_manual_tests.py
          ↓
2. Définir identité/idempotence d'un élément ROBERTO
          ↓
3. Écrire AGENT_STATE.md + AGENT_WORKFLOW.md
          ↓
4. Écrire workflow/marie.yaml
          ↓
5. Implémenter StateMachine comme bibliothèque Python
          ↓
6. Ajouter une CLI mince autour du même moteur
          ↓
7. Brancher ingest_manual_tests.py
          ↓
8. Tester ATTENTE → RECU → ANALYSE → CORRECTIONS → INTEGRE
```

**Donc oui : bibliothèque importable comme chemin principal, CLI comme façade secondaire.** Cela minimise le couplage avec l'existant tout en donnant immédiatement un outil pratique pour tester ROBERTO indépendamment de l'ingestion.
