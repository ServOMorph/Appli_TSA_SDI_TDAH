Je recommande **de ne pas utiliser `ROBERTO/state/marie_state.json` comme un gros journal parallèle**. Ta remarque sur `_contexte/marie_tests_journal.json` est justement importante : les deux fichiers doivent avoir des responsabilités nettement différentes.

### 1. Identité : UUID interne + empreinte de l'événement source

Je ne choisirais **pas le hash du contenu JSON comme seul `id`**.

Je ferais deux niveaux :

```text
id            = UUID interne ROBERTO
source_id     = identifiant stable de l'élément source, si disponible
content_hash  = hash canonique du contenu pertinent
```

Pourquoi ?

Un même contenu peut légitimement apparaître deux fois. Par exemple Marie pourrait renvoyer exactement le même résultat après deux sessions différentes. Un hash du contenu seul transformerait alors ces deux occurrences en un seul élément.

À l'inverse, pour détecter une **réimportation accidentelle du même événement**, le hash est très utile.

Je verrais donc :

```json
{
  "id": "8b7f...",
  "workflow": "marie_tests",
  "state": "RECU",

  "source": {
    "type": "marie_tests_journal",
    "source_id": "test-session-2026-08-18-001",
    "content_hash": "sha256:..."
  },

  "created_at": "...",
  "updated_at": "...",

  "history": [
    {
      "from": "ATTENTE",
      "to": "RECU",
      "event": "json_received",
      "at": "..."
    }
  ]
}
```

Ainsi :

* **UUID** = identité de l'objet dans ROBERTO ;
* **`source_id`** = identité métier/source ;
* **`content_hash`** = mécanisme de détection de doublon.

Et surtout, **le hash ne doit pas inclure les champs volatils** (`updated_at`, état, historique, etc.). Il doit être calculé sur une représentation canonique de l'événement source.

### 2. Je distinguerais même « doublon » et « même contenu »

C'est important pour la suite.

ROBERTO devrait pouvoir répondre à :

> « Est-ce exactement le même événement source que celui que j'ai déjà ingéré ? »

plutôt que :

> « Est-ce que j'ai déjà vu ce contenu quelque part ? »

Je ferais donc idéalement une clé d'idempotence :

```text
source_type + source_id
```

si le journal fournit un identifiant stable.

Et le `content_hash` serait un **contrôle supplémentaire**.

Si le journal actuel ne fournit pas encore de `source_id` suffisamment fiable, on pourra en définir un à partir des champs métier de l'entrée. Je ne figerais pas cette décision avant d'avoir regardé la structure exacte de `_contexte/marie_tests_journal.json`.

## 3. Pour le stockage : un fichier par élément

Entre tes deux options, je préfère nettement :

```text
ROBERTO/state/marie/
├── 8b7f....json
├── 31c2....json
└── ...
```

plutôt que :

```text
ROBERTO/state/marie_state.json
```

avec un énorme tableau.

La raison principale n'est pas seulement la taille. C'est que **l'état est une ressource individuelle**, alors que `_contexte/marie_tests_journal.json` est déjà le journal de données de test.

Cela donne une séparation claire :

```text
_contexte/
└── marie_tests_journal.json
    = données métier / résultats de tests

ROBERTO/state/marie/
├── <uuid>.json
└── ...
    = état d'orchestration ROBERTO
```

Donc ROBERTO ne recrée pas un deuxième journal des tests.

### 4. Et je reprendrais effectivement l'idée `session-XXX`

Ton rapprochement avec `test-results/session-XXX/` est pertinent, mais je ferais une distinction :

```text
test-results/
└── session-XXX/
    = artefacts/résultats de la session

ROBERTO/state/marie/
└── <roberto-id>.json
    = état de traitement de cette entrée
```

Le fichier ROBERTO pourrait d'ailleurs référencer la session plutôt que recopier son contenu :

```json
{
  "id": "8b7f...",
  "workflow": "marie_tests",
  "state": "ANALYSE",

  "source": {
    "type": "marie_test",
    "session_id": "session-XXX",
    "source_id": "marie-2026-08-18-001",
    "content_hash": "sha256:..."
  },

  "history": []
}
```

C'est beaucoup plus sain architecturalement.

---

## 5. Une nuance : je ne mettrais pas forcément l'historique complet dans chaque state

Il y a deux modèles possibles :

**V1 simple :**

```text
ROBERTO/state/marie/<id>.json
```

contient état courant + historique.

**V2 plus robuste :**

```text
ROBERTO/state/marie/<id>.json
ROBERTO/events/marie/<id>.jsonl
```

Le premier contient :

```json
{
  "id": "...",
  "state": "ANALYSE",
  "updated_at": "..."
}
```

et le `.jsonl` contient les transitions :

```text
ATTENTE → RECU
RECU → ANALYSE
```

Pour **l'Étape 1**, je resterais sur la V1. Elle est beaucoup plus simple à implémenter et tester.

Mais je définirais dès `AGENT_STATE.md` que **l'historique des transitions appartient conceptuellement à ROBERTO**, et non au journal de tests.

# Donc je modifierais ma proposition initiale

Au lieu de :

```text
ROBERTO/
├── AGENT_WORKFLOW.md
├── AGENT_STATE.md
├── workflow/
│   └── marie.yaml
└── state/
    └── marie_state.json
```

je partirais sur :

```text
ROBERTO/
├── AGENT_WORKFLOW.md
├── AGENT_STATE.md
├── workflow/
│   └── marie.yaml
└── state/
    └── marie/
        └── <roberto-uuid>.json
```

avec, pour chaque entrée :

```text
UUID ROBERTO
    │
    ├── état courant
    ├── identité de la source
    ├── hash du contenu source
    ├── timestamps
    └── historique des transitions
```

Et **aucune copie du payload complet de `_contexte/marie_tests_journal.json`**, sauf nécessité ponctuelle.

### Le point que je vérifierais avant de créer ces fichiers

Il y a une petite étape préalable que je n'avais pas suffisamment mise en avant dans ma réponse précédente : **inspecter précisément le schéma actuel de `marie_tests_journal.json` et `scripts/ingest_manual_tests.py`**.

C'est là qu'on pourra décider proprement si `source_id` existe déjà, quels champs constituent l'identité d'un retour, et exactement quelle partie doit entrer dans `content_hash`.

Je ne créerais donc pas encore `marie_state/` à l'aveugle. **La toute première action technique de l'Étape 1 devrait être cet audit du format d'entrée existant**, puis seulement la définition du contrat d'identité ROBERTO.
